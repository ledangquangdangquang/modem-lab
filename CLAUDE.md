# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Goal

Next milestone: send actual **audio** (a sound clip → quantized to bits) over the wired link and play the decoded audio back on the laptop, using **QPSK** (2 bits per symbol, I/Q) instead of BPSK. The BPSK code described below is the current working baseline, not the target — keep it working (loopback BER = 0) as the reference while QPSK is added. Status: working over the real cable — `Tx_qpsk.m`/`Rx_qpsk.m` (200 blocks, BER 0, EVM ≈ 6%) and `Audio_qpsk.m` (1 s of 8 kHz / 8-bit audio = 64000 bits at 4000 baud, 10.6 s frame, BER 0/64000 and 0/8000 audio samples wrong, reproduced on two separate real recordings; a 3 s clip = 192000 bits, 29.8 s frame, was also run over the real cable: 2/192000 bits wrong, BER ≈ 1e-5, EVM 14.6%). Audio is sent as a whole file and played back afterwards, not streamed, so the bit rate only sets how long the frame is. Fractional-sample timing was tried in a scratch experiment on that recording (linear interpolation of `mf`: 2 → 0 wrong bits, EVM 14.6 → 12.7%, gain only where the clock drifts; the ≈10% EVM floor elsewhere is noise/analog filtering) and judged not worth adding at this BER. Still to do: your own/longer audio clips, then wireless/underwater.

Longer-term targets, after the wired QPSK audio link works: the same modem over a **wireless** channel (through-the-air acoustic) and an **underwater** channel. Unlike the cable, both have multipath and (underwater) Doppler/time-varying delay, so the per-block pilot zero-forcing equalizer and early-late drift tracking will likely not be enough — expect to need a real channel estimator/equalizer. The final goal is **underwater with coherent QAM**, not the professor's BFSK: reuse the patent's zero-padded frame + frequency-domain equalizer (it doesn't depend on the modulation), but send M-QAM symbols. `Tx_qam.m`/`Rx_qam.m` are the start of that path. Only side experiments exist so far: `air_wireless/` (a BPSK over-the-air fork, never run: no `tx_air*`/`rx_air*` output exists) and `underwater_ofdm/` (a simulation-only OFDM time-sync study). The main modem scripts don't assume those channels yet (the "no multipath" note below is true only for the cable).

## What this is

A wired audio-modem link in MATLAB: the laptop is the real Tx and Rx. It generates a 2-PAM (BPSK) baseband signal, writes it to a .wav, that file is copied to a phone which just plays it back as the analog source; the laptop records the played-back audio over a headphone cable (line-in/mic, not through-the-air acoustic) and must decode it back to the original bits, checking bit error rate. So the "channel" is the cable + phone speaker/DAC + laptop ADC — no multipath, but real clock/gain mismatch between the two devices (hence CFO estimation and sample-clock drift tracking). No build system, package manager, linter, or test framework — this is exploratory research code, run interactively in MATLAB (`Fs`, `Fc`, `baud_rate`, etc. end up as workspace variables). The top level is a git repo (initialized 2026-11-18, see `.gitignore`: `Thay_Khuong/`, `papers/`, `MFSK_tx_rx/`, `.venv/` and regenerable Tx wavs are ignored; real recordings `rx_*.wav` and their `tx_params*.mat` are tracked). `tx_rx_basic/` (the old separate repo with manual copies) is no longer used: don't copy files there. `README.md` is the user-facing overview (Vietnamese).

- `Tx.m` — builds a 2-PAM frame (50-bit known preamble for sync/CFO estimation, then 20 blocks of `[pilot bit, 10 data bits]`), modulates it to a passband square-pulse waveform at `Fc`, writes it via `audiowrite` to `tx_cable.wav`, and saves every parameter + the generated bits/signal to `tx_params.mat` so `Rx.m` can reload them in a fresh MATLAB session. Copy `tx_cable.wav` to the phone and play it.
- `Rx.m` — reloads `tx_params.mat` if the workspace is empty, then picks its input via `RX_SOURCE`: `'loopback'` (default — decodes `tx_signal` in-memory, no phone/cable needed, BER should be exactly 0), `'record'` (records real audio via `audiorecorder`, dumping what it captured to `rx_debug.wav` for post-mortem), or `'file'` (re-decodes a previously saved `rx_debug.wav` via `audioread`, without needing to record again — only valid when that wav still matches the currently-loaded `tx_params.mat`/`data_bits`; a stale pairing from an earlier `Tx.m` run silently decodes against the wrong bits and reads as BER≈0.5, not a channel/noise problem). Demod chain: downconvert to complex baseband (I/Q) → matched filter (integrate-and-dump) → cross-correlate against the preamble waveform to find frame start, sweeping a coarse CFO grid first so a real offset can't self-cancel the correlation → estimate carrier frequency offset from the phase step between consecutive preamble symbols (not a polyfit/unwrap over the whole preamble — one bad sample can make unwrap jump a false 2π) → per-block zero-forcing equalization using the pilot symbol, with a small early-late search per block to track sample-clock drift between phone and laptop → 2-PAM slicer → `biterr` against the original bits, plus per-block error/timing printouts for diagnosing whether errors are random noise or growing clock drift.
- `Tx_qpsk.m` / `Rx_qpsk.m` — QPSK copies of `Tx.m`/`Rx.m` (the BPSK originals are untouched, keep it that way). Same frame layout, but blocks are `[pilot symbol, 5 QPSK data symbols]` (Gray map, `(±1±j)/√2`), the preamble stays real ±1 so the sync/CFO code is identical, and the passband is `real(bb·e^{j2πFc t})` (I·cos − Q·sin). Pilot ZF `g = mf/pilot_sym` is complex, so it removes carrier-phase rotation as well as gain. They use their own `tx_params_qpsk.mat`/`tx_cable_qpsk.wav`/`rx_debug_qpsk.wav`, and `Rx_qpsk.m` always reloads its `.mat` (`RX_SOURCE` at the top of the file selects loopback / record / file). Both scripts and `Tx.m`/`Rx.m` share variable names (`tx_signal`, `data_bits`, …): run `clear` when switching between BPSK and QPSK in one MATLAB session or `Rx.m` will decode against the wrong workspace bits (BER≈0.5). `Tx_qpsk.m` sends 200 blocks (2000 bits, ~1.25 s). `Rx_qpsk.m` tracks CFO and pilot timing in segments of `M=10` blocks instead of one CFO for the whole frame: per segment, two rounds of pilot-phase-slope CFO refinement with the position anchored at the segment start (a CFO error only multiplies 10 blocks, not the whole frame), then a ±2-sample timing pick by pilot coherence over the segment. Why: on the real link (phone → cable → laptop) the clock mismatch is NOT constant over a long frame — in a 10.6 s frame CFO was ≈ −24 Hz for ~2.6 s then ≈ 0 (pilot timing offset plateaus ≈ 433 samples), reproducibly on two recordings. The earlier whole-frame CFO refinement (K=20→80→…, drift derived from CFO) diverged after the change (−25 → −48 Hz, BER 0.499). Per-block `max|mf|` timing is unreliable too: the pilot is one of the 4 constellation points, so |mf| is flat over many samples whenever a neighbouring symbol equals it (noise-free loopback jittered ±3 samples → EVM floor 4% at sps=48, 15% at sps=12) — that is why timing is picked by coherence over a segment. Details in `qpsk/docs/bai_hoc.md`. It prints EVM: loopback ≈ 0%, real cable at 1000 baud ≈ 6%, at 4000 baud (sps=12) ≈ 15–17% (integer-sample sampling, sampling error up to half a sample; fractional interpolation not done). Verified: loopback BER = 0 (also with a 13-sample delay); simulated constant 0.3% clock mismatch, and a mismatch that changes mid-frame (0.3% → −0.05% at 3 s), both BER 0/64000; real cable, 200 blocks at 1000 baud: BER 0/2000, CFO ≈ −24.4 Hz (≈0.3% clock mismatch), pilot timing drifting 4→179 samples (≈3.7 symbols at sps=48), EVM 6.2%. Sync peak/median is meaningless when the recording has exact-zero silence (median ≈ 0 → 1e16); trust BER. Long frames print only summaries (per-block lists only when ≤ 300 blocks). `Rx_qpsk.m` has hooks so `Audio_qpsk.m` can reuse it: `params_file`/`rx_wav`/`audio_src`/`record_time` are read if already set, otherwise they default to the QPSK files (constants, so running it by hand is unaffected).
- `Audio_qpsk.m` — a *function* (`Audio_qpsk('tx')`, `('rx')`, `('rx','loopback')`, `('rx','file')`) that sends an audio clip through the QPSK modem. `'tx'` (`Audio_qpsk('tx', 'giong.wav', 3)`: file and seconds are optional args; default = MATLAB's built-in `handel.mat`, 1 s; 3 s of audio → 192000 bits, 29.8 s frame, loopback BER 0; the `giong.wav` now in the folder is 3.0 s mono 8 kHz 16-bit; it has since been run over the real cable, see Result below): file → mono → `resample` to `audio_fs` = 8 kHz → first `audio_sec` s → 8-bit uniform quantization (MSB first) → 64000 bits → same `[pilot, 5 symbols]` frame as `Tx_qpsk.m` (own ~12-line copy) at `baud_rate` = 4000 (sps=12; 1000 is the level verified earlier — lower it if BER > 0) → `tx_cable_audio.wav` + `tx_params_audio.mat` (also `audio_q`, `n_audio`, `audio_fs`). `'rx'`: sets `record_time` = frame length + 3 s, calls `Rx_qpsk` unchanged (runs in the function's own workspace, so no stale-variable BER≈0.5 pitfall), packs bits back into samples, prints the wrong-sample count, writes `rx_audio.wav` and plays it. It records to `rx_debug_audio.wav`: keep it (`'file'` re-decodes it) and never overwrite a real recording with a simulated one. The modem is payload-agnostic — the audio-specific parts are only quantization and re-assembly (no compression, no unequal error protection). Result: two real 1 s recordings, BER 0/64000, 0/8000 samples wrong; and the current `rx_debug_audio.wav` + `tx_params_audio.mat` pair is a real 3 s / 192000-bit recording (19200 blocks): unchanged `Rx_qpsk.m` gives 2/192000 bits wrong, EVM 14.6%, CFO ≈ −21 Hz for the first seconds then ≈ 0, pilot timing offset plateaus ≈ 420 samples.
- `Tx_qam.m` / `Rx_qam.m` — M-QAM (`M_qam`, default 16) with the zero-padded frequency-domain equalizer from the professor's BFSK patent (`papers/Dang_ky_bang_sang_che_FSK_Ver 2409_23h.pdf`): frame `[preamble ±1 | 0 | header | 0 | data | 0 | header | 0 | …]`, header = Zadoff-Chu (`Lh`=31), zero guard `Lz` (symbols, must exceed channel delay spread + `mg`=2), data = `n_sub`×[pilot, 5 QAM symbols]. Rx: sections 1–5 copied from `Rx_qpsk.m`, plus an FIR lowpass before I&D (removes the 2·Fc image that leaks once echoes/drift misalign the I&D window); per block: residual CFO from the two header halves → `H = FFT(header+0)/FFT(header)`, truncated to `Lz` taps → MMSE `conj(H)Y/(|H|²+nv)` → pilots give residual CFO slope and mean gain. Own files `tx_params_qam.mat`/`tx_cable_qam.wav`/`rx_debug_qam.wav`; `RX_SOURCE` adds `'sim'` (3-path echo 0/1.3/3.7 ms, 0.3% clock mismatch, passband SNR). Verified in sim only, not on the real cable yet: loopback BER 0 (EVM ≈1%, square-pulse image floor); 16-QAM 1000 baud on the sim channel 1/4000 (a 1-tap equalizer gives 776/4000); 64-QAM 0/6000 at SNR 20. At 4000 baud there is an EVM floor ≈7–12% even at high SNR, caused by the square pulse (not the clock); the fix is RRC pulse shaping, not done.
- `Plot_qpsk.m` — a plotting script to run *after* `Rx_qpsk.m` in the same workspace (it needs `tx_signal`, `rx_raw`, `rx_bb`, `mf_out`, `eq_all`, `data_bits`, `Fs`). It draws 3 figures: (1) `tx_signal`, `rx_raw`, then I and Q of `rx_bb` overlaid with `mf_out` against time, with the three Rx axes x-linked; (2) the first 60 data symbols after pilot ZF against the ideal Tx symbols (I, Q, and |error|); (3) two-sided `pwelch` spectra (dB/Hz, centred) of the four signals, showing the ±Fc peaks, the −2·Fc image in `rx_bb`, and that image attenuated in `mf_out`. It does not work after `Audio_qpsk('rx')`, because that runs `Rx_qpsk` inside the function's workspace.
- `test.m` — a standalone demo of the coarse CFO grid sweep from step 4 of `Rx_qpsk.m`. It builds a synthetic 20-bit preamble at Fs = 44100 Hz and sps = 20, adds a 47 Hz CFO and light noise, sweeps −500:15:500 Hz, prints the grid error, and plots the correlation peak against CFO, then |xcorr| with and without compensation. It starts with `clear; clc; close all`, so running it **wipes the workspace**: re-run `Tx*`/`Rx*` afterwards.
- `air_wireless/Tx_air.m` / `Rx_air.m` — a BPSK fork of `tx_rx_basic/Tx.m`/`Rx.m` for through-the-air acoustic (phone speaker → laptop mic, no cable); untested, since no `tx_air.wav`/`rx_air_debug.wav` exists anywhere. Differences from the cable version:
  - 1.5 s padding instead of 0.5 s, and a fixed `record_time = 8` s;
  - `RX_SOURCE` defaults to `'record'`;
  - sync picks the **earliest local maximum** of |xcorr| above 70% of the global peak, instead of `max`, so it locks onto the direct path rather than a stronger later reflection;
  - everything after sync (preamble CFO, per-block `max|mf|` early-late ±3 search, pilot ZF) is the old BPSK `Rx.m` chain, not the segment tracking of `Rx_qpsk.m`.

  Path pitfall: `Tx_air.m` writes `tx_air.wav`/`tx_air_params.mat` to the *current directory*, but `Rx_air.m` loads `.mat`/`.wav` from its *own folder*, so `cd air_wireless` before running both. Like `Rx.m`, `Rx_air.m` only reloads the `.mat` when `Fs` is not already in the workspace, so the same stale-workspace BER≈0.5 pitfall applies.
- `underwater_ofdm/` — simulation-only reproduction of the HUST paper "A Multi-Stage Method for Time Synchronization in Acoustic Underwater Communications" (Nguyen Van Huy et al., `papers/Nguyen van huy paper_255.pdf`). It is an OFDM time-sync study, separate from the QAM/patent path. Files:
  - `build_ofdm_symbol.m` — one real-valued OFDM symbol via a Hermitian-symmetric IFFT, `[0, c, conj(fliplr(c))]`, plus a cyclic-prefix GI. Length K = 2·NFFT + nGI + 1.
  - `uw_sync.m` — the paper's proposed multi-stage GI-similarity sync, eqs. (2)–(8): P, Q, R, SYN, then CQ/CR, then C. Eqs. (6)–(7) were OCR-damaged in the paper and are *interpreted* here as centred local `movsum` windows of length nGI; re-check them if the original equations or code turn up.
  - `uw_sync_reference.m` — the paper's "reference scheme [7]": SYN = Q·R with a 1/3-of-peak threshold, taken from `Thay_Khuong/Matlab Programs/OFDM_DOPPLER_STUDENTS/reciever.m`.
  - `sim_uw_sync_mse.m` — Monte-Carlo MSE and failure rate against SNR (1–4 dB, NFFT = 1024, nGI = 512, 200 trials), to reproduce the shape of the paper's Fig. 8. It adds a synthetic 1–3-echo multipath channel (`USE_MULTIPATH`), because with AWGN alone both schemes always succeeded, which did not match the paper. That channel is made up, not measured.

  No results are saved, so re-run it to get numbers.

## Working with the MATLAB scripts

- Variable names are the API: `Fs` (sample rate), `Fc` (carrier), `baud_rate`, `sps` (samples per symbol = `Fs/baud_rate`) recur across files and must stay consistent within a run. `Tx.m` sets them; `Rx.m` either inherits them from the workspace or reloads them from `tx_params.mat`.
- Comments are in Vietnamese; keep new comments consistent with that if extending these files, unless told otherwise.
- The demod chain's ordering matters and is not obviously reorderable: downconvert → matched filter (integrate-and-dump) → sync via preamble cross-correlation (with the coarse CFO sweep) → CFO estimate/correct on the *found* preamble segment → symbol sampling with per-block drift tracking → pilot-based equalization → slice. Changing one stage's indexing (e.g. `start_idx`, `data_start`, `blk_off`) has to stay in lock-step with how the preamble/pilots were laid out at Tx.
- There's no automated test; "correctness" is checked by eye via the printed `Errors`/`BER`/per-block timing and the `scatterplot`/`plot` figures each script produces at the end. When changing the modem logic, re-run with `USE_LOOPBACK = true` first and check BER is 0 before testing over the real cable.

## Explaining code to the user

- When asked to explain a line/formula, work a **small concrete example** by hand: tiny numbers (e.g. `sps = 4`, a 2-symbol preamble), a table of sample index → value, and a table showing what the code computes at a few indices, including the right one and off-by-one neighbours, so the user sees why the formula is exactly what it is. Numbers first, general formula second.

## Explaining complex numbers to the user

- Write complex samples/symbols as magnitude∠phase (`r∠θ`), never as rectangular `a+jb`, unless the user asks for rectangular form. Multiplication in this domain (e.g. CFO correction `exp(-j*2*pi*cfo_hz*n/Fs)`) is naturally "multiply magnitudes, add angles" — showing it as `a+jb` products obscures that.
- Say **"ký hiệu" (symbol)** for one transmitted bit's waveform — spans `sps` samples, indexed per-bit (e.g. `preamble_sym(k)`, `sym_val(k)`, one point per data bit after equalization). Say **"mẫu" (sample)** for one point in an `Fs`-rate array (e.g. `rx_raw(n)`, `mf_out(n)`, `rx_bb(n)`) — `sps` samples make up one symbol. Don't use the two interchangeably.
